# Kodik → Payload pipeline

Самостоятельный Python-пайплайн для импорта каталога из **Kodik API** в PostgreSQL/Payload CMS и постеров в MinIO/S3.

## Что нового (v2.8) — даты серий

- **Перепроверка тайтлов с новыми сериями без даты.** Раньше не-онгоинг проверялся в AniList один раз, и если `sync-dubs` создавал серии позже, их даты так и оставались пустыми. Теперь уже проверенный тайтл проверяется повторно, если у него есть серии без `airing_at`, их число изменилось с прошлой проверки, и прошло не меньше `--recheck-days` дней (по умолчанию 3). Состояние (`data/schedule-state.json`) помнит, сколько серий осталось без даты после проверки (`missing`), поэтому тайтл, которого нет в расписании AniList, не опрашивается бесконечно. Тайтлы, которых нет в AniList, перепроверяются только с `--all`.
- Порядок прежний: `sync-dubs` → `sync-schedule`. Тесты: `tests/test_schedule_recheck.py` (без БД).

## Расписание серий из AniList (v2.7) — `sync-schedule`

Команда берёт расписание эфира из AniList и пишет его в БД. Тайтл находится **по `content.shikimori_id`**: Shikimori использует id MyAnimeList, а в AniList это `idMal` — без поиска по названию, который мог выбрать не тот сезон. Запрос проверен на реальных данных (Bleach: Thousand-Year Blood War, idMal 41467).

```bash
python pipeline.py sync-schedule --dry-run --limit 5     # пробный прогон на нескольких тайтлах
python pipeline.py sync-schedule                         # первый запуск: онгоинги + разовая проверка остальных
python pipeline.py sync-schedule --only-ongoing          # для крона: только онгоинги
```

**Что пишется**
- `episodes.airing_at` — дата эфира серии, Unix-секунды (формат поля `airingAt` в CMS; сайт уже показывает её как дату выхода). Серии **не создаются** — их создаёт `sync-dubs`; по ним расписание заполняется на следующем запуске, так что порядок `sync-dubs` → `sync-schedule` даёт даты и серий других озвучек.
- `content.next_episode_number` / `content.next_episode_at` — ближайшая невышедшая серия (для бейджа «Серия 15 — сегодня в 18:26» и расписания). Поля добавляются в CMS: `cms/ContentScheduleFields.ts` (+ миграция Payload). Пока колонок нет, шаг пропускается, даты серий всё равно обновляются. У тайтла без ближайшей серии поля очищаются.

**Правила**
- дата заполняется, если её не было; пока серия не вышла, дата следует за AniList (эфир переносят); **вышедшие серии с датой не перезаписываются** (`--overwrite` — перезаписать всё);
- если у content несколько строк сезонов (многосезонный сериал или дубли — см. `fix-seasons`), серии не трогаются: по одному расписанию нельзя понять, какому сезону оно относится; «следующая серия» при этом пишется;
- онгоинги проверяются при каждом запуске, остальные — один раз (файл состояния `data/schedule-state.json`; `--all` — перепроверить всё). Тайтлы, которых нет в AniList, повторно не запрашиваются;
- работа кусками по 50 тайтлов: сеть → короткая транзакция → сохранение состояния; при сбое уже записанное не теряется, упавший тайтл повторится при следующем запуске;
- пауза между запросами `--delay 0.8` с (лимит AniList около 90 запросов в минуту; при 429 пайплайн сам ждёт `Retry-After`);
- `airingAt` — время **эфира в Японии**; озвучка на сайте появляется позже, в интерфейсе пишите «эфир», а не «выйдет на сайте».

Тесты: `tests/test_anilist.py`, `tests/test_schedule_db.py`.

## Другие озвучки у серий (v2.6) — `sync-dubs`

Серия по-прежнему одна на `(season_id, episode_number)` и хранит ссылку основной озвучки (`KODIK_TRANSLATION_ID`, AniLibria = 609) в `episodes.player_link` — `load`, `update-ongoing`, `fix-seasons` и сайт работают как раньше. Остальные озвучки лежат в отдельной таблице **`episode_sources`**: одна строка на пару (серия, озвучка) со ссылкой на плеер. Это второй вариант из заметки ниже («плееры отдельной коллекцией»): ключ серий не меняется, дублей серий нет.

**Порядок:**
1. В CMS добавить коллекцию `EpisodeSources` — файл `cms/EpisodeSources.ts` (внутри инструкция) — и применить миграцию Payload. Таблицу создаёт CMS, а не пайплайн.
2. Убедиться, что у нужных озвучек заполнен `kodikTranslationId`: `match-voiceovers --write`, затем `sync-voiceovers`.
3. `python pipeline.py sync-dubs --dry-run`, затем `python pipeline.py sync-dubs`.

```bash
python pipeline.py sync-dubs --only anidub shiza-project   # только эти озвучки (slug или id Kodik)
python pipeline.py sync-dubs --ongoing-only                # только онгоинги — быстрый режим для расписания (запускать после update-ongoing)
python pipeline.py sync-dubs --no-create-episodes          # только ссылки озвучек, без новых серий
python pipeline.py sync-dubs --max-pages 1 --dry-run       # проверка
```

**Как это работает:**
- для каждой озвучки справочника с `kodik_translation_id` идёт запрос Kodik `/list?translation_id=…` (по озвучке — отдельная транзакция, блокировка не держится на время сети);
- тайтл ищется по `shikimori_id` (у записей других озвучек другой Kodik ID); сезоны сопоставляются, только если их число у Kodik и в БД совпадает (номера сверяются по порядку — нумерация франшизы сдвигает «сырые» номера). Неоднозначные случаи пропускаются и попадают в сводку, а не пишутся «наугад»;
- **список серий строится по всем озвучкам, а не только по основной.** Серия, которой нет в БД, но которая есть у другой озвучки, **создаётся** (`title` «Серия N»). Ссылкой по умолчанию (`episodes.player_link`) становится ссылка основной озвучки (`KODIK_TRANSLATION_ID`, она обрабатывается первой), а если у неё серии нет — первой озвучки, у которой серия есть; у существующей серии без ссылки ссылка проставляется. Тайтл при этом помечается обновлённым. Защита от чужой нумерации: номер не может быть больше самого большого существующего в сезоне более чем на `--max-ahead` (по умолчанию 50). Отключается флагом `--no-create-episodes`;
- тайтлы и сезоны не создаются: если тайтла (или подходящего сезона) нет в БД, запись пропускается и попадает в сводку;
- ничего не удаляется; существующая ссылка меняется, только если изменилась; повторный запуск безопасен; `--dry-run` откатывает запись;
- после изменений сбрасывается кэш сайта (`REVALIDATE_URL` / `REVALIDATE_SECRET`);
- код возврата 1 при ошибках или пропуске из-за блокировки — виден в Dokploy Schedules.

**Ограничения:** только сериалы (у фильмов нет серий; ссылка фильма — `content.player_link`); каталог тайтлов по-прежнему строится по основной озвучке, поэтому тайтлы, у которых её нет вообще, в БД не появятся — серии создаются только внутри уже загруженных тайтлов и сезонов; сайт должен сам читать `episode-sources` (в этом репозитории его нет). Полный проход — запрос каталога на каждую озвучку: для расписания используйте `--ongoing-only`, полный — раз в сутки/неделю.

**Какие озвучки добавить.** `match-voiceovers` теперь в конце показывает крупнейшие озвучки Kodik, которых нет в `voiceovers.json` (`--untracked N`, по умолчанию 15). Чтобы подключить: допишите в файл `{"title": "...", "kodikTranslationId": ID}`, затем `sync-voiceovers` и `sync-dubs`.

## Справочник озвучек (v2.5)

Подготовка к связке «серия ↔ озвучка»: в БД заводится справочник из 45 студий (AniLibria, AniDub, JAM CLUB … Kitsune Studio) — файл `voiceovers.json`, команда `sync-voiceovers`.

**Порядок:**
1. В CMS добавить коллекцию `Voiceovers` — готовый файл `cms/Voiceovers.ts` (внутри пошаговая инструкция) — и применить миграцию Payload. Таблицу создаёт CMS, а не пайплайн, чтобы схема не разъезжалась.
2. `python pipeline.py sync-voiceovers --dry-run` — посмотреть, что будет создано; затем `python pipeline.py sync-voiceovers`.

**Как это работает:**
- ключ записи — `slug` (если в файле его нет, строится из названия); id выдаёт БД в порядке списка: 1 — AniLibria … 45 — Kitsune Studio. `--dry-run` не «сжигает» id;
- команда безопасна для повторного запуска: дубли не создаются, неизменившиеся строки не трогаются;
- **ничего не удаляется** — на озвучки будут ссылаться серии. Записи, добавленные в админке и не входящие в файл, остаются (команда пишет их количество);
- запись, созданная вручную с тем же названием (без учёта регистра) и другим slug, приводится к каноническому slug, а не дублируется;
- необязательное поле `kodikTranslationId` в файле — id озвучки в Kodik (для будущего сопоставления); пишется в колонку `kodik_translation_id`, существующее значение пустотой не затирается.

Чтобы добавить студию, допишите объект `{"title": "..."}` в конец `voiceovers.json` и запустите команду. Тесты: `tests/test_voiceovers.py`.

**Id озвучек Kodik — `match-voiceovers`.** Команда скачивает `translations/v2` (токен из `KODIK_TOKEN`, в файлы он не пишется) и ищет каждую из 45 студий по названию без учёта регистра и знаков препинания; окончание «.TV» не мешает («AniLibria» = «AniLibria.TV»), текст в скобках проверяется отдельно («DeliciousDub (ChillDUB)»).

```bash
python pipeline.py match-voiceovers            # только отчёт, ничего не меняет
python pipeline.py match-voiceovers --write    # записать найденные id в voiceovers.json
python pipeline.py sync-voiceovers             # перенести id в БД (voiceovers.kodik_translation_id)
```

Id **не угадываются**: если в Kodik несколько озвучек с одним названием, команда покажет их с числом тайтлов, и id нужно выбрать вручную (или `--pick-largest` — взять самую крупную). Похожие названия — только подсказки. Если студия в Kodik называется иначе, добавьте у записи `"aliases": ["название в Kodik"]` и повторите. Уже записанный id молча не перезаписывается — расхождение выводится в отчёте.

**Связка с episodes.** Решение принято: ключ серии `(season_id, episode_number)` не меняется, озвучки вынесены в отдельную коллекцию «источники серии» — см. раздел «Другие озвучки у серий» выше.

## Что нового (v2.4) — сезоны и франшизы без дублей

- **Нет дублей сезонов.** Раньше сезон искался по `(content_id, season_number)`; номера франшизы пересчитываются при каждом `fetch`, и сезон с новым номером не находился — создавалась вторая строка `seasons` с теми же сериями. Теперь (`kodik_pipeline/seasons.py`) сезон, у которого сменился номер, **получает новый номер**, а не новую строку; точные дубли (тот же номер) объединяются, а строки, все серии которых уже есть в основном сезоне записи из одного сезона, удаляются. Строки с уникальными сериями никогда не удаляются — только попадают в отчёт.
- **Части сезонов** (`kodik_pipeline/franchise.py`). «Часть 2», «Part 2», «Cour 2» в названии → тот же номер сезона, что у предыдущей записи (Сезон 3 · Часть 1 / Часть 2), а не новый сезон. Если в названиях есть явный номер сезона («2 сезон», «Season 3»), части склеиваются только при совпадении номеров. К названию сезона дописывается «Часть N», если её нет в названии (так её видит сайт). У тайтла `title_en`/`slug` получают суффикс `S3` / `S3 Part 2` (`-s3-p2`).
- **Исправлена нумерация франшизы.** `shikimori_id` сортировался как строка (`9999` после `10000`); запись Kodik с несколькими сезонами получала номера только у первого сезона, из-за чего сезон «0» (спецвыпуски) сливался с первым, а следующая запись франшизы получала повторяющийся «Сезон 2». Теперь номера сквозные по всей франшизе, сезон «0» остаётся нулевым.
- **Одинаковый `shikimori_id` = один сезон.** Из дублей остаётся запись с большим числом серий (затем свежее обновление); остальные пропускаются с предупреждением. Если Kodik выдал новый `id` для уже загруженного сезона, `load` находит тайтл по `shikimori_id` и обновляет его, а не создаёт второй.
- **Защита от неполной выдачи.** Номера сезонов существующих записей меняются, только если в данных есть вся франшиза из БД. При `--max-pages` или пропавшем у Kodik сезоне записи переиспользуются, но не перенумеровываются (в логе предупреждение).
- **`update-ongoing`** использует то же сопоставление: запись из одного сезона попадает в строку своего тайтла независимо от «сырого» номера Kodik и не создаёт новых сезонов, даже если в БД уже есть дубли.
- **Новая команда `fix-seasons`** — разовая чистка уже загруженных дублей по `data/kodik.json`, без пересоздания контента:

```bash
python pipeline.py fetch
python pipeline.py fix-seasons --dry-run   # посмотреть, что будет объединено
python pipeline.py fix-seasons
```

Порядок выкладки: пайплайн → `fetch` → `fix-seasons --dry-run` → `fix-seasons` → обычный `sync`. Новые тесты: `test_franchise.py`, `test_seasons_db.py` (на Postgres).

## Что нового (v2.3) — совместимость с обновлённой CMS

- **`load` больше не использует `ON CONFLICT (title_en)`.** Миграция CMS `20261003_120000` удалила уникальный индекс по `title_en` (ремейки и одноимённые тайтлы), и со старым запросом любой `load` падал бы с «no unique or exclusion constraint matching the ON CONFLICT specification». Теперь тайтл ищется по `kodik_id` (индекс есть в CMS); запасной поиск по `title_en` — только среди записей без `kodik_id` и того же `type`. `slug` и `type` существующей записи не меняются — URL стабильны.
- **`content.franchise_id`** (и `_content_v.version_franchise_id`): общий идентификатор сезонов одного сериала. Формат — голый `kinopoisk_id` (или `imdb_id`), как у записей, заполненных миграцией CMS, поэтому франшизы не разъезжаются. Пишется, только если колонка есть.
- **Сброс кэша сайта**: после успешного `load` и `update-ongoing` (с изменениями, не в `--dry-run`) пайплайн сам вызывает `POST <REVALIDATE_URL>/api/revalidate`. Нужны `REVALIDATE_URL` и `REVALIDATE_SECRET`; без них шаг пропускается, ошибки сброса пайплайн не роняют. Вручную: `python pipeline.py revalidate`.
- В `docker-compose.yml` добавлен `init: true` (остановка контейнера без 10-секундной задержки).
- Новые тесты: `test_revalidate.py`, `test_load_lookup.py` и три интеграционных теста (повторный `load` идемпотентен, `_status = 'published'` + `franchise_id`, сброс кэша только после commit).

Порядок выкладки: **CMS (миграции) → пайплайн → один `sync`**. Новые тайтлы пишутся с `_status = 'published'`, иначе публичное чтение CMS их не отдаёт.

## Что нового (v2.2)

- **Новая команда `update-ongoing`** — быстро обновляет серии и статус у сериалов со статусом «выходит» (ongoing), не гоняя весь каталог. Подробнее — в разделе ниже.
- **Статус выхода сохраняется**: `anons` / `ongoing` / `released` пишется в `content.release_status` (колонку создаёт миграция CMS; без неё пайплайн работает как раньше).
- **Защита от параллельных запусков**: `sync`/`load` и `update-ongoing` берут advisory-lock в Postgres — две записывающие задачи одновременно не работают (вторая честно пропускает запуск).
- **`load` больше не падает целиком из-за одной записи**: каждая запись в своём `SAVEPOINT`, битые попадают в отчёт, остальные сохраняются; код возврата 1, чтобы сбой был виден в Dokploy Schedules.
- **`fetch` безопаснее**: запись JSON атомарная (tmp + rename), пустой ответ API не затирает прошлый `data/kodik.json`.
- `fetch_kodik.py` стал тонкой обёрткой над `pipeline.py fetch` (раньше дублировал код); у `sync` появились все API-опции `fetch`.
- Исправлены два падавших теста; добавлены тесты на онгоинги и интеграционные тесты на реальном Postgres (см. «Тесты»).
- Убраны устаревшие упоминания старых скриптов (`merge_kodik_sources.py`, `movies.json` и т.д.) из докстрингов.

## Деплой в Dokploy

Пайплайн — batch-задача, поэтому в Dokploy он запускается как **Compose**-сервис с «спящим» контейнером, а сами команды выполняются по расписанию (Schedules) или вручную через Terminal. Postgres в `docker-compose.yml` не входит: он должен быть отдельным сервисом **Database → PostgreSQL** в том же проекте Dokploy.

1. В проекте создайте **Database → PostgreSQL** (если ещё нет) и скопируйте его **Internal Host**.
2. Создайте сервис **Compose** (тип Docker Compose), источник — git-репозиторий с этим кодом, Compose Path: `./docker-compose.yml`.
3. Во вкладке **Environment** задайте переменные из `.env.example`. Главное:
   `DATABASE_URL=postgres://USER:PASSWORD@<internal-host>:5432/<db>`
   Хост — Internal Host базы, а не `localhost` и не внешний адрес.
4. Compose подключён к внешней сети `dokploy-network`, поэтому контейнер видит Postgres (и MinIO, если он тоже в Dokploy) по внутренним именам. Если включён **Isolated Deployments**, добавьте эту сеть в сервисы Postgres/MinIO или используйте внешние адреса.
5. Нажмите **Deploy**.
6. Во вкладке **Schedules** создайте задачи (тип Compose, Service Name `kodik-pipeline`):

| Задача | Команда | Пример cron |
| --- | --- | --- |
| Импорт каталога | `python pipeline.py sync --genres genres.json` | `0 3 * * *` |
| Постеры | `python pipeline.py posters` | `30 3 * * *` |
| Новые серии онгоингов | `python pipeline.py update-ongoing` | `0 * * * *` |

Кэш сайта сбрасывается автоматически после этих задач, если в Environment заданы `REVALIDATE_URL` (по умолчанию `http://movhub-web:3000` — alias сервиса web в `dokploy-network`) и `REVALIDATE_SECRET` (тот же, что у web и CMS).

`update-ongoing` и `sync` можно ставить на пересекающееся время: если одна задача уже пишет в БД, вторая выведет «запуск пропущен» и завершится (следующий запуск подхватит изменения).

Для разовой проверки откройте **Terminal** контейнера `kodik-pipeline`:

```bash
python pipeline.py check-s3
python pipeline.py fetch --max-pages 1
python pipeline.py update-ongoing --dry-run
```

`data/kodik.json` лежит в томе `kodik_data` (`/app/data`) и переживает передеплой. Схема таблиц Payload (`content`, `episodes`, `media` и т.д.) должна существовать до запуска `load`: CMS должна применить свои миграции к этой БД, включая `add_release_status`.

### MinIO (отдельный сервис)

MinIO разворачивается из шаблона Dokploy (`pgsty/minio`, форк с рабочей консолью) в этом же проекте:

- порт `9000` — S3 API (домен API), порт `9001` — консоль (основной домен);
- `MINIO_BROWSER_REDIRECT_URL` — публичный адрес консоли;
- `S3_ENDPOINT=http://minio:9000` — внутренний адрес, работает, если оба Compose в сети `dokploy-network` (Dokploy подключает её сервисам с доменами). При Isolated Deployments имя может отличаться — смотрите Internal Host / имя сервиса;
- бакет (`media`) создаётся вручную в консоли; пайплайн его не создаёт;
- чтобы постеры открывались по `S3_PUBLIC_URL`, у бакета нужна анонимная политика чтения (Anonymous → `readonly`/download для префикса `*`);
- `check-s3` выведет бакеты, видимые с текущим ключом.

## Обновление онгоингов (`update-ongoing`)

```bash
python pipeline.py update-ongoing              # обычный запуск
python pipeline.py update-ongoing --dry-run    # показать изменения и откатить их
python pipeline.py update-ongoing --no-recheck # без перепроверки завершившихся
```

Что происходит:

1. Запрашиваются только сериалы со статусом `ongoing` (фильтры `anime_status` и `all_status`; результат дополнительно фильтруется на стороне пайплайна, поэтому лишнее не попадёт, даже если API проигнорирует фильтр).
2. Тайтл ищется в БД по `kodik_id`. Новые серии добавляются, изменившиеся ссылки на плеер обновляются, у тайтла обновляется `updated_at`. Существующие серии без изменений не трогаются.
3. Сезон Kodik сопоставляется с уже существующим сезоном в БД, поэтому перенумерация франшиз (S2/S3) не ломается.
4. Пишется `release_status`.
5. Тайтлы, которые в БД числятся `ongoing`, но пропали из списка Kodik (обычно сериал завершился), перепроверяются отдельным запросом по Kodik ID: фиксируется новый статус и финальные серии. Лимит — `--recheck-limit` (по умолчанию 200). Работает только при наличии колонки статуса.

Тайтлы, которых ещё нет в БД, **не создаются** (иначе нумерация сезонов франшизы была бы неверной) — команда выводит их список, они появятся при ближайшем `sync`. Если Kodik вернул ноль онгоингов, БД не трогается и команда завершается с ошибкой (похоже на сбой API).

`--max-pages` предназначен для проверок; с ним перепроверка пропавших автоматически отключается, т.к. список неполный.

### Колонка статуса

Статус хранится в `content.release_status` и `_content_v.version_release_status` (enum `anons` / `ongoing` / `released`, поле `releaseStatus` в коллекции Content). Колонки создаёт **миграция CMS** `20260928_193844_add_release_status` — она применяется автоматически при старте CMS, вручную ничего добавлять не нужно.

Порядок выкладки: сначала деплой CMS, затем один `sync` (проставит статусы всему каталогу), затем расписание `update-ongoing`.

- В БД пишутся только `anons`, `ongoing`, `released`; любое другое значение Kodik превращается в пустое (иначе enum отверг бы всю запись).
- Другое имя колонки — переменная `RELEASE_STATUS_COLUMN` (нужно только при собственной схеме).
- Пока миграция не применена, пайплайн не падает: серии добавляются, но статус не сохраняется и завершившиеся сериалы не перепроверяются (в логе будет примечание).

### Фон (backdrop) из скриншота

Шаг `posters` помимо постера берёт **первый скриншот** из API (`material_data.screenshots[0]`; если он невалидный — первый корректный http(s)-URL), загружает его в S3/MinIO как `<slug>-backdrop.<ext>`, создаёт запись `media` и ставит её в `content.backdrop` (и в версии `_content_v`).

- Заполняется только **пустой** `backdrop`: фон, выбранный редактором, не перезаписывается (и скриншот в этом случае даже не скачивается).
- Тайтл ищется по `kodik_id` (если есть), иначе по `title_en`.
- `load` теперь копирует `poster_id` / `backdrop_id` из `content` в пересозданные версии, так что картинки не пропадают из админки после повторной загрузки.
- Чтобы заполнить уже загруженный каталог, один раз выполните `python pipeline.py posters`.

### SEO-поля CMS

В CMS подключён SEO-плагин (миграция `20261006_120000_add_seo_meta`): у `content` есть `meta.title`, `meta.description`, `meta.image`. Пайплайн заполняет их из данных Kodik API:

| Поле | Источник |
| --- | --- |
| `meta.title` | `titleRu` + год + «— смотреть онлайн», до 60 символов (длинное название обрезается с «…») |
| `meta.description` | описание из API (HTML/BBCode и пометка «Источник» убираются), до 155 символов по границе слова; если описания нет — шаблон из названия, года и жанров |
| `meta.image` | постер (проставляет шаг `posters`) |

- `load` заполняет `title`/`description`, `posters` — картинку.
- Значения пишутся **только в пустые поля**: то, что отредактировано в админке, не затирается (но и автоматически не обновляется, если Kodik изменит описание).
- `load` пересоздаёт строки `_content_v`, поэтому `meta_*` копируются из `content` в версии — иначе админка (она показывает последнюю версию) не увидела бы значения.
- Чтобы заполнить уже загруженный каталог, один раз выполните `load` и `posters`. Без миграции CMS шаг пропускается.

## Настройки Kodik

```env
KODIK_LIMIT=100
KODIK_DELAY=0.25
KODIK_TIMEOUT=60
KODIK_RETRIES=5
RELEASE_STATUS_COLUMN=release_status   # необязательно
```

Пайплайн следует URL из поля `next`/`next_page`. Параметр `page` вручную не используется.

Повторяются временные ошибки 429/500/502/503/504 и сетевые ошибки. Для 429 учитывается `Retry-After`, если сервер его вернул. При зацикленной ссылке `next` выполнение прекращается с ошибкой.

## Данные

Источник: `GET https://kodik-api.com/list` с `with_episodes=true`, `with_material_data=true`, `translation_id` и `limit`.

Результат нормализации содержит фильмы и сериалы в едином формате. Для сериалов сохраняются сезоны и эпизоды с `playerLink`. Записи сериалов с одинаковым `kinopoisk_id` (или, при его отсутствии, одинаковым `imdb_id`) группируются в франшизу.

`genres.json` — канонический справочник. Если он передан в `load`, таблица жанров синхронизируется с ним; неизвестные жанры создаются как fallback и записываются в `unmapped_genres.json`.

## Постеры

```bash
python pipeline.py posters --data data/kodik.json
```

Дополнительные ограничения:

```bash
python pipeline.py posters --data data/kodik.json --timeout 20 --retries 3 --max-bytes 10485760
```

Перед загрузкой проверяется `Content-Type`, размер ответа ограничивается `--max-bytes`, затем изображение сохраняется в S3/MinIO и привязывается к `content`/последней версии Payload.

## Безопасность

**Никогда не коммитьте рабочие `KODIK_TOKEN`, `DATABASE_URL`, S3 secret/access keys.** Если настоящий токен когда-либо попал в git, архив или публичный канал, его следует перевыпустить в кабинете Kodik.

`.env.example` содержит только плейсхолдер `YOUR_KODIK_TOKEN_HERE`.

## Тесты

```bash
pytest -q
```

Юнит-тесты покрывают нормализацию, пагинацию, статусы, выборку онгоингов, атомарную запись JSON, сезоны/эпизоды, richText, жанры, slug и рейтинг.

Интеграционные тесты (`tests/test_integration_db.py`) запускаются на БД, в которой применены миграции CMS (`pnpm payload migrate` в проекте CMS), и проверяют `load` и `update-ongoing` на реальном Postgres: перенумерованные сезоны, dry-run, сохранение статуса, перепроверку завершившихся, изоляцию битых записей и advisory-lock. Без переменной они пропускаются:

```bash
TEST_DATABASE_URL=postgres://user:pass@127.0.0.1:5432/test_db pytest -q
```

⚠ Эти тесты **очищают** таблицы Payload (`TRUNCATE`) — используйте только отдельную тестовую БД. Схему они не меняют.
